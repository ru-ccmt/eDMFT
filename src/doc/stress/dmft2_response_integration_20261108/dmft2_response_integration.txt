DMFT2 -> RESPONSE INTEGRATION
8 November 2026

EXECUTION POLICY
run_dmft.py runs the response ONCE, after its outer charge/eDMFT loop ends.
Intermediate charge and EF-only steps never run response, even with STRT or
STRFT in case.in2[c]. Early convergence is handled exactly like reaching the
iteration limit. The normal loop computes lapw0/lapw1 after its last mixer;
these final potentials/vectors feed one additional measurement pass:

  dmft2 -> screened response -> lcore -> SCF assembly -> mixer

This extra pass is necessary because convergence is only known after the
preceding mixer and occupation checks. There is no extra impurity solve.
Response failure aborts the pass before lcore/mixer. A killed/failed run does
not execute a final response. Runs with no response request retain the ordinary
sequence. The final measurement adds a normal SCF record; it does not add an
impurity iteration or an info.iterate impurity row.

Standalone x_dmft.py dmft2 runs the requested response immediately after dmft2.
The two wrappers share src/python/dmft2_step.py and the same failure checks.

HOW TO REQUEST IT
Set the first token in the actual case.in2 or case.in2c to:

  STRT     native analytic stress plus a final response request
  STRFT    native analytic stress and forces plus a final response request

These are Python-wrapper aliases. Native dmft2 is given STR or STRF through a
temporary IN2/DEF pair; the original files remain byte-for-byte unchanged.
Other tokens and all other input records are preserved. Native WIEN programs
have not been taught five-character modes: keep case.in0 at its native STR
setting, and do not pass STRT/STRFT directly to an unmodified lapw2 executable.

Alternatively keep native STR/STRF and create case.stress_response.json:

{
  "enabled": true,
  "solver": {
    "wien_root": "/Users/haule/wien2k_24",
    "dmft2": "/Users/haule/dbin/dmft2_response",
    "mpi": ["/opt/homebrew/bin/mpirun", "-n", "4"],
    "strain": 0.00025,
    "probe_step": 0.00001,
    "tolerance": 0.02,
    "max_iterations": 25
  }
}

The JSON is optional for STRT/STRFT. Defaults use WIENROOT, dmft2_response
beside the installed dmft2, and the usual MPI2 launch prefix as arguments.
Set solver.mpi explicitly for site prefixes containing shell expansions.
Paths are interpreted relative to the calculation directory. The default
workspace root is case.response_runs; workspace_root can change it.

"enabled": false overrides STRT/STRFT. Controls are reread at execution time.
There is intentionally no every-N option in run_dmft: the user requested only
the final iteration. A standalone --no-response suppresses that one request.

EDITABLE PREPARED INPUTS
Normal x_dmft.py dmft2 retains its historical preparation and sigma-splitting
steps. For files already prepared/split, use:

  ~/dbin/x_dmft.py --execute-only dmft2

This executes the existing dmft2.def, case.indmf2, and sig.inpN without
regenerating them. Use -l dn for the corresponding existing dmft2dn.def when
running an ordinary magnetic step; the response backend itself is not yet
magnetic. The -d preparation-only option never executes a response.

run_dmft.py still performs its existing Prepare_dmft2 and SSplit operations.
The shared executor does not add any further preparation, and the final pass
uses the already prepared files. Editing those files retains the same
between-preparation-and-execution semantics as before.

OUTPUTS AND WHAT THEY MEAN
case.stress_response.status.json states whether this execution is disabled,
deferred_until_final, running_dmft2, running_response, complete, failed, or
skipped_noncharge. It is replaced atomically. A deferred/disabled/failed step
invalidates an earlier published result; it never reuses an old correction.

A successful request creates a unique directory under case.response_runs:
  reference/           snapshot of physical inputs and localized DEF files
  reference.json       input/executable hashes and reference identity
  config.json          effective solver settings
  response.log         solver diagnostics
  screening/report.json
  screening/response.density
  screening/potential_plus/ and potential_minus/

The status file points to outputs and their SHA-256 checksums. Report fields
include the screening residual and the central charge-map residual. Convergence
of screening alone is not proof that the stress formula is complete. Response
children invoke executables directly, so they cannot recursively trigger the
wrapper response hook. They work in isolated copies, not in the parent case.

CURRENT SCIENTIFIC SCOPE
The integrated backend computes a hydrostatic, fixed-Sigma, fixed-N density
response and physical endpoint potentials. It currently supports nonmagnetic,
no-SOC, primitive orthogonal cells, normalized projector 5, fixed band indices,
and recomputeEF=1. Unsupported fixed-mu or magnetic cases fail explicitly.
The backend uses serial WIEN lapw1 for its fixed-G reference, and MPI dmft2.
It still performs repeated response actions; the matrix-only optimization is
not yet substituted into this solver.

This integration DOES NOT yet apply a corrected stress to mixer. The portable
backend does not yet produce the complete validated radial plus normalized-
projector stress contraction. The status explicitly records stress_applied=false.
The separate stress_response_result.py retains independent radial/projector
selection for validated diagnostic records. It is not silently enabled here.
Adding a hydrostatic scalar to a general tensor would be unjustified. Existing
analytic stress/forces continue through the normal SCF/mixer path.

RELIABILITY
The core step must return zero, report DMFT2 END, and leave empty error files.
Fortran STOP failures returning zero are therefore caught. Input translations
are cleaned up on failure. A nonblocking lock prevents concurrent response
requests in the same case directory from overwriting status. Parent prepared
inputs, sigma, density, potential, vector and energy files are not changed by
the response. dmft2 itself still writes its normal outputs (including EF.dat).

TESTS
Tests cover final-only scheduling, explicit disabling, EF-only bypass, both
aliases, temporary-file cleanup, missing/invalid controls, stale-result
invalidation, concurrent execution, native zero-status error stops, supported
ensemble checks, and failure preventing later lcore/mixer calls.
The isolated SrVO3 end-to-end result is recorded separately in the checkpoint.
